# 第 11 章导读:推理工程 —— API 服务 / 流式 / 工具调用

> 这是 MiniMind 教程的第 11 章。完整的交互版见 [`ch11.ipynb`](./ch11.ipynb)。

## 章节摘要

前面所有章节都在解决「怎么训练模型」,本章解决最后一个工程问题:**如何把模型变成一个可用的服务**。

训练完的 `.pth` 文件不能被外部程序调用。本章用 FastAPI 搭建 OpenAI 兼容的 `/v1/chat/completions` 端点,实现 SSE 流式输出,解析 `<think>` 和 `<tool_call>` 标签,最后把模型转换为 HF transformers 格式以部署到 vllm / ollama。

核心决策:采用 OpenAI API 格式(事实标准),让 minimind 零成本接入 LangChain、Cursor、各种 Agent 框架。

## 学习目标

读完本章后,你应该能:

- 解释为什么 OpenAI `/v1/chat/completions` 是事实标准,以及采用它的生态优势
- 用 FastAPI + Pydantic 搭建一个 OpenAI 兼容的 chat completions 端点
- 解释 SSE 流式的三层管道:TextStreamer → Queue → StreamingResponse
- 手写 `parse_response` 函数:从模型输出中分离 `<think>`(reasoning_content)和 `<tool_call>`(tool_calls)
- 解释 `open_thinking` 参数的多字段兼容设计
- 说出模型格式转换的必要性:`.pth` → HF transformers → vllm / ollama / llama.cpp
- 解释为什么映射到 `Qwen3Config`(专用 kernel 优化),以及 MoE expert stacking 的原理
- 演示 LoRA 合并流程:$W' = W + BA$
- 描述 `eval_toolcall.py` 的多轮工具调用评估循环

## 术语表

| 术语 | 英文 | 解释 |
|---|---|---|
| 推理服务 | Inference Server | 把模型封装为 HTTP 接口供外部调用 |
| OpenAI 兼容 | OpenAI-compatible | API 格式与 OpenAI `/v1/chat/completions` 一致 |
| 服务器推送事件 | SSE (Server-Sent Events) | HTTP 流式传输协议,`data: {...}\n\n` 格式 |
| 首字延迟 | TTFT (Time To First Token) | 用户等待第一个 token 的时间 |
| 流式器 | Streamer / TextStreamer | transformers 提供的逐 token 回调机制 |
| 推理内容 | reasoning_content | `<think>` 标签内的模型推理过程 |
| 工具调用 | tool_call / function calling | 模型请求调用外部工具的结构化指令 |
| 模型格式转换 | Model Conversion | `.pth` → HF transformers / GGUF 等格式 |
| 专家堆叠 | Expert Stacking | MoE 模型把独立 expert 合并成 stacked tensor |
| LoRA 合并 | LoRA Merge | $W' = W + BA$,把 LoRA 折叠进基模权重 |
| 持续批处理 | Continuous Batching | vllm 的动态拼批技术,提升并发吞吐 |
| 分页注意力 | PagedAttention | vllm 的 KV cache 内存管理优化 |

## SSE 流式管道

```
model.generate()          CustomStreamer              Queue              StreamingResponse
  │  逐 token 生成          │  decode → text          │  线程安全队列       │  SSE 格式输出
  │ ──────────────────→    │ ──────────────────→    │ ──────────────→  │ ──────────────→ client
  │                         on_finalized_text          queue.put(text)     "data: {...}\n\n"
```

## 输出解析规则

| 模型原始输出 | 解析后字段 | 消费者 |
|---|---|---|
| `<think>推理内容</think>` | `message.reasoning_content` | 前端(可选展示) |
| `<tool_call>{"name":"f",...}</tool_call>` | `message.tool_calls` | Agent 框架(程序执行) |
| 剩余正文 | `message.content` | 用户(最终回答) |

## 核心认知

> 推理工程不是「调参」,而是**协议设计 + 工程管道**。OpenAI API 格式是事实标准;SSE 流式把 TTFT 从秒级降到百毫秒级;模型格式转换让 minimind 零成本接入整个推理生态(vllm / ollama / llama.cpp)。掌握这三件事,模型就从「实验室产物」变成了「生产服务」。
